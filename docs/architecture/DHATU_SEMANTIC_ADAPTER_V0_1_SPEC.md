# Спецификация: Sanskrit Dhatu Semantic Adapter v0.1 (Research PoC)

**Проект:** AAM-Language-Kernels / SOL-Triad-Engine  
**Документ:** Спецификация независимого семантического адаптера  
**Статус:** SPECIFICATION / PENDING IMPLEMENTATION  
**Дата:** 2026-10-30  

---

## 1. Назначение и архитектурные границы

**Sanskrit Dhatu Semantic Adapter v0.1** — это изолированный исследовательский прототип, предназначенный для проверки гипотезы о том, что канонический словарь из 32 санскритских корней (`Dhatu`) может служить устойчивым промежуточным семантическим языком для нормализации естественно-языковых инженерных запросов.

### Жесткие ограничения прототипа:
1. **Отсутствие вмешательства в SOL-Triad:** Прототип не модифицирует детерминированное ядро SOL-Triad, Python reference engine, существующие TypeScript-сервисы, JSON-схемы и Workbench UI.
2. **Изолированность вычислений:** Адаптер **не производит** инженерных расчетов, симуляций состояний или физического управления. Его единственная задача — семантический разбор, классификация и формализация пользовательского намерения в контракт `Canonical Semantic Intent (CSI)`.
3. **Принцип независимой авторизации (Security by Architecture):** 
   * *Архитектурная коррекция:* Наличие поля `"execution_authorized": false` в выходном CSI от языкового модуля **ничего не гарантирует** само по себе. Это лишь рекомендательная метаданная. 
   * Принимающая сторона (`SolTriadJsonAdapter` и детерминированный движок) обязана независимо верифицировать структуру, проверять наличие всех необходимых физических параметров и осуществлять политику авторизации как отдельный механизм, независимо от уровня уверенности (`confidence`) языковой модели.

## 2. Разрешение семантических нюансов: разбор трёх базовых предложений

Для проверки способности адаптера различать тонкие инженерные смыслы рассмотрим три внешне похожих, но семантически различных запроса:

### Предложение 1: *«Уменьшить температуру двигателя»*
- **Инженерный смысл:** Активное управляющее воздействие или коррекция рабочего режима (операция воздействия на состояние).
- **Ключевые Dhatu:** `√kri` (TRANSFORM / действие), `√tapa` (HEAT_FLOW / объект воздействия).
- **Роль в SOL-Triad:** Соответствует процессу рассеяния или управляемому воздействию в `DISSIPATE` (state delta или resource cost).

### Предложение 2: *«Отвести избыточное тепло от двигателя»*
- **Инженерный смысл:** Организация канала отвода тепла, утилизация тепловой энергии (структурный процесс рассеяния).
- **Ключевые Dhatu:** `√kamp` (DAMP / подавление, отвод), `√tapa` (HEAT_FLOW), `√pranali` (CHANNEL / путь отвода).
- **Роль в SOL-Triad:** Прямое отражение примитива `DISSIPATE` (loss domain, thermal entropy dissipation).

### Предложение 3: *«Не допустить повышения температуры выше 80 °C»*
- **Инженерный смысл:** Установление жесткого инвариантного ограничения (граница допустимого состояния).
- **Ключевые Dhatu:** `√hri` (LIMIT / ограничение), `√tula` (COMPARE / сравнение с порогом), `√bhitti` (BOUNDARY / граница).
- **Роль в SOL-Triad:** Чистый примитив `CONSTRAINT` (`max_bounds: { temperature: 80.0 }`, units: `°C` или `K`).

*Вывод:* Прототип должен доказать способность отличать **ограничение** (`CONSTRAINT`) от **процесса рассеяния/воздействия** (`DISSIPATE`), не допуская смешивания ролей.

## 3. Спецификация выходного контракта v0.1 (Canonical Semantic Intent)

Адаптер на выходе должен формировать строго типизированную структуру:

```json
{
  "intent_id": "string (uuid)",
  "source_language": "ru | uk | en",
  "original_text": "string",
  "dhatu_operations": [
    {
      "sequence_order": 1,
      "dhatu_root": "√hri | √tapa | √man | ...",
      "canonical_meaning": "LIMIT | HEAT_FLOW | MEASURE | ...",
      "target_parameter": "temperature | pressure | energy | null",
      "assigned_sol_role": "SOURCE | CONSTRAINT | DISSIPATE | UNRESOLVED"
    }
  ],
  "extracted_parameters": {
    "parameter_name": "numeric_value"
  },
  "extracted_units": {
    "parameter_name": "unit_symbol"
  },
  "constraints_inferred": {
    "max_bounds": {},
    "min_bounds": {},
    "protected_values": {}
  },
  "missing_parameters": [
    "list_of_unresolved_required_fields"
  ],
  "ambiguities_detected": [
    "description of ambiguous phrasing or conflicting intents"
  ],
  "provenance": {
    "adapter_version": "0.1-poc",
    "timestamp": 1740000000.0
  },
  "confidence": 0.85,
  "execution_authorized": false
}
```

## 4. План тестового набора (Test Suite)

Для первичной валидации адаптера v0.1 формируется банк из **30 предложений** (по 10 на английском, русском и украинском языках):

1. **Группа терминов температуры и тепла (10 фраз):**
   - RU: «Уменьшить температуру двигателя», «Отвести избыточное тепло», «Не допустить превышения 80 градусов».
   - UK: «Знизити температуру двигуна», «Відвести надлишкове тепло», «Не допустити перевищення 80 градусів».
   - EN: «Decrease engine temperature», «Dissipate excess heat», «Prevent temperature from exceeding 80 °C».
2. **Группа давления и потоков (10 фраз):**
   - Контроль давления, срабатывание сбросного клапана, проверка герметичности.
3. **Группа неопределенности и отсутствия параметров (10 фраз):**
   - Запросы без указания численных порогов, фразы с двусмысленными формулировками, попытки несанкционированного изменения защищенных контуров.

## 5. Критерии успешности прототипа v0.1

1. **Семантическая дифференциация:** Успешное разделение запросов ограничения (`CONSTRAINT`) и запросов рассеяния (`DISSIPATE`) на трех языках.
2. **Точность извлечения единиц и чисел:** Сохранение исходных числовых знаков и единиц (`бар`, `К`, `°C`) без галлюцинаций отсутствующих данных.
3. **Безопасность авторизации:** Во всех тестовых сценариях поле `execution_authorized` строго возвращает `false`, фиксируя пропущенные параметры в `missing_parameters`.
