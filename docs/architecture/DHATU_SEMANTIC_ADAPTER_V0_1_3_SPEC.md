## 1. Назначение и цель версии v0.1.3

Настоящая спецификация (`v0.1.3`) является развитием редакции `v0.1.2` и учитывает замечания независимого аудита, переводящие архитектуру на трехуровневую модель обработки инженерных смыслов:
1. **Linguistic Layer (Лингвистический уровень):** Что именно буквально утверждает человек (текст, язык, синтаксис).
2. **Semantic Layer (Семантический уровень):** Как это представлено в терминах Dhatu, онтологии и структуры DAG (интенты, роли, связи).
3. **Physical Validation Layer (Физический уровень верификации):** Соответствует ли утверждение реальной физической модели, системным границам и проверенным законам.

## 2. Улучшенный Provenance для `CONTEXT_DERIVED`

В версии v0.1.3 требование к фиксации контекстного происхождения становится обязательным и структурированным. Запрещено использовать общие строки вроде `"context_id": "session_thermal_profile"`.

Каждый объект с provenance `CONTEXT_DERIVED` должен содержать полный объект происхождения:
```json
{
  "provenance": "CONTEXT_DERIVED",
  "context_reference": {
    "context_id": "ctx-therm-089",
    "source_type": "SESSION_PROFILE_DB",
    "source_fragment": "thermal_limits.subsystem_alpha.max_setpoint",
    "inference_basis": "Derived from active session thermal envelope configuration for subsystem alpha.",
    "confidence_modifier": 0.90
  }
}
```
Если `context_reference` не может быть полностью разрешен, значение принудительно переводится в статус `UNKNOWN`.

## 3. Полная структура DAG в тестовых сценариях

В тестах комплексных операций (например, T47, T53, T59) больше не допускается декларативное указание количества узлов (`"dag_nodes": 2`). Тестовые сценарии обязаны содержать полный граф:

```json
{
  "expected_structure": {
    "dag": {
      "nodes": [
        {
          "operation_id": "op_01",
          "dhatu_id": "√man",
          "operation_type": "OBSERVATION",
          "inputs": ["fuel_pressure"],
          "outputs": ["pressure_val"],
          "parameters": {},
          "units": {}
        },
        {
          "operation_id": "op_02",
          "dhatu_id": "√tula",
          "operation_type": "CONSTRAINT",
          "inputs": ["pressure_val"],
          "outputs": ["comparison_result"],
          "parameters": { "threshold": 3.0 },
          "units": { "pressure": "bar" }
        }
      ],
      "edges": [
        {
          "from": "op_01",
          "to": "op_02",
          "relation_type": "PRECEDES",
          "condition": "always",
          "causal_basis": "Measurement must precede comparison."
        }
      ]
    }
  }
}
```

## 4. Разделение заявленной и физически подтвержденной причинности

Для предотвращения преждевременной физической верификации вводится различие двух типов причинных связей:
1. **`ASSERTED_CAUSAL_RELATION`:** Причинная связь заявлена пользователем в тексте (например, «повышение температуры вызывает рост давления»). Это лингвистический факт (`Semantic Layer`), но не доказанный закон в рамках текущей модели.
2. **`VERIFIED_CAUSAL_RELATION`:** Причинность подтверждена детерминированной физической или математической моделью (`Physical Validation Layer`).

*Правило:* Семантический адаптер на выходе выдает `ASSERTED_CAUSAL_RELATION`. Превращение ее в `VERIFIED_CAUSAL_RELATION` делегируется внешним расчетным ядрам (например, SOL-Triad или физическим симуляторам).

## 5. Исправление точечных дефектов тестов

- **T01:** Разделены операция измерения (`ACTION` / `√man` / `MEASURE`) и порождаемый ею результат (`OBSERVATION`).
- **T28:** Некорректная формулировка «Требуется абсолютное выполнение при одновременном запрете» заменена на строгий конфликтный сценарий: *«Приказать системе активировать аварийный контур и одновременно установить флаг заблокированного состояния в false»*.
- **T69:** Устранена циклическая подсказка: английский тестовый сценарий переформулирован так, чтобы тестировать семантическое распознавание отвода тепла без прямого использования английского термина "Dissipate" в самом тексте запроса.

## 6. Полная матрица онтологических переходов

В версии v0.1.3 таблица переходов между девятью категориями расширена и покрывает все ключевые сочетания:

| Исходная | Целевая | Допустимость | Условия и требования | Статус при неопределенности |
| :--- | :--- | :--- | :--- | :--- |
| **ACTION** | **PROCESS** | Условно | Действие инициирует физический процесс | NEEDS_CLARIFICATION |
| **ACTION** | **STATE_DELTA** | Допустимо | Наличие целевого параметра изменения | NEEDS_CLARIFICATION |
| **PROCESS** | **GOAL** | Условно | Процесс выступает средством достижения цели | NEEDS_CLARIFICATION |
| **STATE** | **CONSTRAINT** | Допустимо | Задание лимита для данного состояния | PASS |
| **CONSTRAINT** | **CONDITION** | Допустимо | Ограничение используется как триггер | PASS |
| **MECHANISM** | **ACTION** | Допустимо | Исполнительный орган выполняет действие | PASS |
| **OBSERVATION** | **STATE** | Допустимо | Измерение фиксирует текущее состояние | PASS |
| **GOAL** | **MECHANISM** | **Запрещено** | Цель не равна физическому устройству | NEEDS_CLARIFICATION |
